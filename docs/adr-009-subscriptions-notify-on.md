# ADR-009: хранение notify_on в подписках

## Контекст

US-CART-02: подписки на изменения товара (на MVP — только событие
`in_stock`/`low_stock`). Нужно решить, как хранить набор типов событий в строке
подписки.

## Рассмотренные варианты

| Вариант | Простота фильтрации по типу события | Сложность миграции при новом типе |
| --- | --- | --- |
| **ArrayField / JSON-массив** | Средняя: нужны операторы `ANY`/`contains`, индексы по элементам | Низкая: просто добавить значение в enum, миграция данных не нужна |
| **Отдельная таблица событий** (M:N subscription↔event) | Высокая: join при каждом запросе рассылки | Средняя: новая строка в справочнике событий, без изменения схемы подписки |
| **String-колонка (один тип на строку)** (выбрано) | Высокая: простой `WHERE notify_on = ?`, индекс по колонке | Средняя: добавление типа = новое значение в enum + backfill при необходимости |

## Решение

Выбран **String-столбец с одним типом события на строку**: одна подписка — одна
строка с `notify_on` (enum `in_stock`/`low_stock`). Фильтрация рассылки
тривиальна (`WHERE notify_on = 'in_stock'`), индекс простой. Дубликаты по паре
`(user_id, sku_id)` запрещены уникальным ограничением. Добавление нового типа
события — новое значение enum и, при необходимости, backfill существующих строк;
это проще, чем join-таблица, и предсказуемее, чем JSON-массив.

## Последствия

* Плюс: простая схема, простые запросы, минимум миграций на MVP.
* Плюс: уникальность `(user_id, sku_id)` даёт 409 при дубликате «из коробки».
* Минус: один тип события на подписку — если понадобится несколько типов на один
  SKU, потребуется либо несколько строк, либо миграция на M:N-схему.
* Минус: отправка уведомлений вне scope этого квеста — сейчас только сохранение
  и отписка.
