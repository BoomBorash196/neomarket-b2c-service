# ADR-010: идентификация гостевой корзины

## Контекст

US-CART-03: корзина покупателя для гостя (без авторизации) и авторизованного
пользователя, с merge при логине. Нужно выбрать, как идентифицировать гостевую
корзину и как связывать её с авторизованным покупателем.

## Рассмотренные варианты

| Вариант | Совместимость с мобильными клиентами | Риск подделки идентификатора |
| --- | --- | --- |
| **`X-Session-Id` заголовок** (выбрано для гостя) | Высокая: любой HTTP-клиент (мобильное приложение, SPA, curl) ставит заголовок без cookie-инфраструктуры | Средний: клиент генерирует UUID сам; подделка чужой сессии возможна, но ущерб ограничен (только корзина, без PII и резерва) |
| **Cookie** | Низкая для нативных мобильных клиентов (нужен cookie-jar, CSRF-защита) | Низкий при HttpOnly+Secure+SameSite, но усложняет кросс-доменные сценарии |
| **Временный JWT (гостевой токен)** | Высокая | Низкий (подпись проверяется), но требует выдачи и ротации токенов, усложняет гостевой flow |

## Решение

Выбран **`X-Session-Id` для гостевой корзины** и **`X-User-Id` (JWT proxy) для
авторизованного покупателя**.

Аутентифицированный пользователь приходит с доверенного источника (`X-User-Id`,
выставляемого шлюзом из JWT); гость — с `X-Session-Id`. Для корзинных операций,
которые могут выполняться и для гостя, используется резолв владельца
(`X-User-Id` или `X-Session-Id`). Merge гостевой корзины в авторизованную выполняет
MAX по количеству на SKU; гостевые строки не удаляются после merge
(идемпотентность).

## Последствия

* Плюс: простая интеграция для любых клиентов, без cookie/JWT-инфраструктуры.
* Плюс: merge детерминированный и идемпотентный.
* Минус: идентификатор гостевой сессии генерируется клиентом — возможна подделка
  чужой гостевой корзины (ограниченный ущерб: только корзина, без PII и резерва).
* Минус: при потере сессии гостевая корзина недоступна — стандартное поведение
  для гостевых корзин.
