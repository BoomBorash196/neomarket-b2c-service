# ADR-001: Расчёт фасетов в каталоге B2C

## Контекст
B2C-сервис должен возвращать фасетные подсчёты (количество товаров для каждого значения фильтра: бренд, ценовой диапазон и т.д.) для UI-фильтров каталога.

## Решение
Выбран подход **он-лайн расчёт через B2B (proxy + normalise)**. B2C отправляет текущий контекст фильтрации в B2B, получает готовые фасеты и нормализует ответ в `FacetBucket`-формат.

## Альтернативы рассмотрены

| Подход | Консистентность | Нагрузка на БД | Задержка |
|--------|-----------------|----------------|----------|
| SQL GROUP BY на каждый запрос | Высокая (read-your-writes) | Очень высокая (полный scan + group) | Высокая |
| Кэш фасетов с TTL (Redis/in-memory) | eventual consistency (TTL) | Низкая (кэш) | Низкая |
| Денормализованные счётчики (отдельная таблица) | eventual consistency (обновление при изменении товара) | Низкая (pre-aggregated) | Низкая |

## Критерии выбора

1. **Консистентность данных** — фасеты должны отражать актуальное состояние каталога. Подход с он-лайн запросом к B2B даёт read-your-writes консистентность, что критично для покупателя.
2. **Нагрузка на БД** — SQL GROUP BY на каждый запрос неприемлем при большом каталоге (тысячи SKU). Денормализованные счётчики требуют сложной логики обновления при каждом изменении товара. Кэш с TTL вводит задержку согласования.
3. **Простота** — прокси-подход минимален в реализации, не требует доп. инфраструктуры (Redis) и не вводит race conditions при обновлении товаров.

## Итог
Выбран он-лайн прокси-подход. При росте каталога (>100k SKU) планируется миграция на кэш фасетов с TTL 5–10 сек.
