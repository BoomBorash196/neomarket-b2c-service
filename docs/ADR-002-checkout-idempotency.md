# ADR-002: Checkout Idempotency Storage Strategy

## Context

Checkout — критическая операция: деньги списываются, товар резервируется. Двойной клик по кнопке «Оформить» может создать два заказа. Нужно гарантировать, что одинаковый `POST /api/v1/orders` с тем же `Idempotency-Key` вернёт существующий заказ, а не создаст дубликат.

## Decision

Используем **уникальный индекс на `idempotency_key` в таблице `orders`** (database-level constraint) плюс `request_hash` для обнаружения переиспользования ключа с другим телом запроса.

Колонка `idempotency_key` (`VARCHAR(128)`, unique, nullable, миграция `002`) и `request_hash` (`VARCHAR(64)`, миграция `006`) находятся в таблице `orders`. Заказ вставляется со статусом `CREATED` **до** вызова B2B reserve: `INSERT` захватывает ключ атомарно. При повторном запросе с тем же ключом и телом возвращается существующий заказ; если тело отличается — `409 IDEMPOTENCY_KEY_REUSED`. После успешного reserve заказ переводится в `PAID`, сохраняются `OrderItem` со снимком цен, корзина очищается.

## Options Considered

### Option 1: Unique index на idempotency_key в orders (выбрано)
- **Про:** Максимальная надёжность — гарантия на уровне БД. Race condition обрабатывается через UNIQUE constraint: конкурентные запросы с одинаковым ключом — один проходит `INSERT`, второй получает `IntegrityError`, ловится и возвращает существующий заказ.
- **Про:** Нет внешних зависимостей (Redis, Memcached). Работает в любой SQL-базе.
- **Минус:** `IntegrityError` — «медленный путь» при коллизиях, но для checkout коллизии редки.

### Option 2: Redis для ключей
- **Про:** Быстрая проверка (O(1)), TTL для автоматического освобождения «зависших» ключей.
- **Минус:** Дополнительная зависимость (Redis). Race condition при `SET NX` требует Lua-скриптов. Если Redis упал — checkout не работает.

### Option 3: Отдельная таблица-кэш ключей
- **Про:** Изолированная проверка от бизнес-данных.
- **Минус:** Двойная запись (ключ + заказ) — нужна transactional outbox или saga. Сложнее в реализации, чем уникальный индекс.

## Rationale

Уникальный индекс выбран по двум критериям:

1. **Поведение при race condition:** два одновременных запроса с одним ключом — PostgreSQL/SQLite гарантируют, что только один `INSERT` пройдёт. Второй получает `IntegrityError` и возвращает заказ победителя. Это атомарно и безопасно.
2. **Простота реализации:** ноль дополнительных зависимостей. Одна колонка и индекс; работает с SQLite в тестах и PostgreSQL в проде.

## Consequences

- `Idempotency-Key` передаётся в **заголовке** запроса (обязателен по OpenAPI) и уникален для попытки checkout.
- Заказ создаётся и ключ захватывается до B2B reserve; при ошибке reserve транзакция откатывается, ключ освобождается.
- Повтор с тем же ключом и телом → `201` с существующим заказом; другое тело → `409 IDEMPOTENCY_KEY_REUSED`.
- Ключи не очищаются автоматически. При необходимости можно добавить cron-удаление ключей старше N дней (TTL по OpenAPI — 1 час).
