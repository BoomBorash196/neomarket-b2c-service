# ADR-002: Checkout Idempotency Storage Strategy

## Context

Checkout — критическая операция: деньги списываются, товар резервируется. Двойной клик по кнопке "Оформить" может создать два заказа. Нужно гарантировать, что одинаковый POST /orders с тем же idempotency_key вернёт существующий заказ, а не создаст дубликат.

## Decision

Используем **уникальный индекс на `idempotency_key` в таблице `orders`** (database-level constraint).

Колонка `idempotency_key` (VARCHAR(128), unique, nullable) добавлена в таблицу `orders`. При первом POST с ключом — создаётся заказ. При повторном POST с тем же ключом — INSERT с UNIQUE violation → перехватывается через IntegrityError и возвращается существующий заказ.

## Options Considered

### Option 1: Unique index на idempotency_key в orders (выбрано)
- **Про:** Максимальная надёжность — гарантия на уровне БД. Race condition обрабатывается через UNIQUE constraint (конкурентные запросы с одинаковым ключом — один проходит INSERT, второй падает с IntegrityError, который ловится и возвращает существующий заказ).
- **Про:** Нет внешних зависимостей (Redis, Memcached). Работает в любой SQL-базе.
- **Минус:** IntegrityError — "медленный путь" при коллизиях (запрос идёт до конца, падает, обрабатывается). Но для checkout это не проблема — коллизии редки (пользователь не успевает нажать дважды за время выполнения reserve).

### Option 2: Redis для ключей
- **Про:** Быстрая проверка (O(1)), TTL для автоматического освобождения "зависших" ключей.
- **Минус:** Дополнительная зависимость (Redis). Race condition при SET NX требует Lua-скриптов. Если Redis упал — checkout не работает.

### Option 3: Отдельная таблица-кэш ключей
- **Про:** Изолированная проверка от бизнес-данных.
- **Минус:** Двойная запись (ключ + заказ) — нужна transactional outbox или saga. Сложнее в реализации, чем уникальный индекс.

## Rationale

Уникальный индекс выбран по двум критериям:

1. **Поведение при race condition:** При двух одновременных запросах с одним ключом — PostgreSQL/SQLite гарантируют, что только один INSERT пройдёт. Второй получит IntegrityError, который перехватывается exception handler'ом и возвращает существующий заказ. Это атомарно и безопасно.
2. **Простота реализации:** Ноль дополнительных зависимостей. Одна миграция — одна колонка. Работает с любым DB-движком (SQLite для тестов, PostgreSQL для прода).

## Consequences

- `idempotency_key` генерируется на фронтенде (UUID v4) и передаётся в теле запроса.
- При UNIQUE violation (IntegrityError) exception handler в main.py возвращает 409 CONFLICT с существующим заказом.
- Ключи не очищаются — это нормально, так как checkout — финальная операция. Если нужен cleanup, можно добавить cron-запрос на удаление ключей старше N дней.
