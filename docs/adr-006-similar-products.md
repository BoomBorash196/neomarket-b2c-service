# ADR-006: Блок похожих товаров — алгоритм выборки

## Контекст

US-CAT-04 требует блок «Похожие» на карточке товара: до 8 товаров из той же
категории, текущий товар исключён, при нехватке — добор из родительской
категории, при отсутствии — пустой список. Канон также требует, чтобы запрос
алгоритма выборки проксировался в B2B: у B2C нет собственной копии каталога.
Ответ — массив `CatalogProductCard` (`b2c/openapi.yaml`,
`/api/v1/catalog/products/{product_id}/similar`), параметр `limit` 1..50.

## Рассмотренные варианты

| Вариант | Сложность на MVP | Консистентность при повторных запросах |
| --- | --- | --- |
| **Случайная выборка `ORDER BY RANDOM()`** | Низкая, но требует прямого доступа к БД каталога, которого у B2C нет; пришлось бы дублировать данные или просить у B2B несуществующую операцию | Низкая: каждый запрос даёт новый набор, блок «прыгает» при переоткрытии карточки, ответы не кэшируются |
| **Наибольшее совпадение характеристик** | Высокая: нужно получить характеристики всех кандидатов категории и посчитать пересечения; B2B не отдаёт операцию массового сравнения, это N+1 запросов | Средняя: результат детерминирован при неизменных данных, но зависит от полноты характеристик у продавцов |
| **Делегирование B2B: `GET /public/products/{id}/similar` + добор из родительской категории** | **Низкая**: одна операция из опубликованного контракта B2B плюс уже существующий листинг по `category_id`; фильтрацию видимости (MODERATED, наличие) делает B2B | **Высокая**: детерминированный порядок (B2B отдаёт выборку в стабильном порядке, добор — `created_desc`), одинаковый ответ на повторный запрос, возможен кэш на фронте/CDN |

## Решение

Выбран третий вариант — проксирование выборки в B2B. Критерии: сложность
реализации на MVP и консистентность при повторных запросах. Опубликованная
операция `GET /public/products/{id}/similar?limit=` уже реализует подбор по
категории на стороне B2B, поэтому B2C не дублирует алгоритм и не заводит
локальную копию каталога (требование канона). Консистентность важнее
«случайного разнообразия»: покупатель, вернувшийся на карточку, видит тот же
блок, а ответ можно кэшировать. Сложность варианта с совпадением характеристик
не оправдана на MVP: нужны данные, которых нет в одной операции B2B.

## Последствия

- B2C запрашивает `limit + 1` строку, чтобы компенсировать возможное попадание
  текущего товара, и дополнительно исключает его и дубликаты.
- Если в категории меньше `limit` товаров, список добирается через
  `GET /public/products?category_id=<parent>&sort=created_desc`; ошибка добора
  не фатальна — возвращается то, что дала основная выборка.
- Нет похожих совсем → `200 []` (фронт скрывает блок); неизвестный или
  заблокированный товар → `404 PRODUCT_NOT_FOUND`.
- По умолчанию `limit = 8` по канон-flow; контракт разрешает до 50.
