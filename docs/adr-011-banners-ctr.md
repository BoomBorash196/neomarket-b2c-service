# ADR-011: хранение аналитики кликов баннеров (CTR)

## Контекст

US-CART-04: баннеры на главной и CTR-аналитика. Нужно выбрать, как хранить
события кликов по баннерам.

## Рассмотренные варианты

| Вариант | Нагрузка на БД при большом трафике главной | Простота агрегации CTR |
| --- | --- | --- |
| **Запись в реляционную таблицу на каждый клик** (выбрано) | Высокая: один INSERT на клик, но клики редки относительно просмотров | Высокая: `GROUP BY banner_id` с `count(*)`, тривиальные индексы |
| **Батчевая запись** (накопление в памяти/очереди, периодический flush) | Низкая: один INSERT на батч | Средняя: нужна очередь и планировщик, возможна потеря при сбое |
| **Внешняя аналитическая система** (ClickHouse/BigQuery) | Минимальная для БД приложения | Средняя: отдельная инфраструктура и пайплайн |

## Решение

Выбрана **реляционная таблица на каждый клик** (`banner_click_events`: один ряд
на событие с `banner_id`, `user_id`, `created_at`). Для MVP трафик кликов
умеренный, агрегация CTR тривиальна (`GROUP BY banner_id`), и не нужна
дополнительная инфраструктура. Индекс по `banner_id` ускоряет выборку.

## Последствия

* Плюс: простая схема, простая агрегация, нет новых зависимостей.
* Плюс: событие валидируется синхронно (неизвестный баннер → 400).
* Минус: при большом трафике INSERT на каждый клик может стать узким местом —
  в этом случае перейти на батчевую запись или внешнюю аналитику.
* Минус: отправка уведомлений/отчётов вне scope — только сохранение события.
