# ADR-007: иерархия категорий и хлебные крошки

## Контекст

US-CAT-05 добавляет навигацию: плоский список категорий, дерево, детали
категории и хлебные крошки (`category_id` **или** `product_id`). Каталог
принадлежит B2B: `GET /api/v1/categories` (read-open) отдаёт плоский список
`CategoryResponse` с `parent_id` (adjacency list), `level` и `path`
(materialized path строкой). B2C собственной БД каталога не имеет, поэтому
вопрос — как хранить и обходить иерархию на стороне B2B и как читать её в B2C.

## Рассмотренные варианты

| Вариант | Скорость запроса хлебных крошек | Сложность обнаружения orphan node |
| --- | --- | --- |
| **ltree (PostgreSQL)** | O(depth) одним индексным запросом (`@>` / `ltree_ops`), самый быстрый на больших деревьях | Средняя: нужен `parent_id` + триггеры/CHECK, чтобы `ltree`-путь не расходился с ссылками; нужен extension и миграции |
| **Adjacency list + рекурсивный CTE** | O(depth) на рекурсивный запрос к БД; в B2C — один плоский запрос и O(depth) в памяти | Низкая: parent отсутствует во множестве id — orphan виден сразу, цикл ловится обходом |
| **Materialized path** | O(1) — путь уже строка (`electronics/phones`, разбить по `/`) | Высокая: orphan не выражается явно (путь может указывать на несуществующего предка), путь ломается при перемещении узла |

## Решение

Выбран **adjacency list (`parent_id`)**: B2B уже хранит дерево именно так,
B2C читает весь плоский список одним запросом `GET /api/v1/categories` и
строит цепочки в памяти по `parent_id`. `level` и `path`-массив из
`CategoryRef` **вычисляются** на B2C, а не берутся из B2B: контракт B2C
требует `path` как массив строк (хлебные крошки), тогда как B2B отдаёт
materialized path строкой. Отсутствующий родитель или цикл — это `422
ORPHAN_NODE`, а не тихое перевешивание узла в корень; неизвестный id — `404
CATEGORY_NOT_FOUND`.

Критерии выбора:

1. **Скорость хлебных крошек** — один запрос к B2B + O(depth) в памяти;
   рекурсивный CTE на стороне B2B дал бы то же по сложности без второго
   источника правды.
2. **Сложность обнаружения orphan node** — O(1) lookup по словарю id;
   для materialized path понадобилась бы сверка пути с реальными предками,
   для ltree — триггеры и extension.

## Последствия

* Плюс: нет миграций, extension'ов и дублирования каталога в B2C; любая
  правка дерева в B2B сразу видна навигации.
* Плюс: битая иерархия честно всплывает как 422 при первом же запросе
  затронутой ветки, а не превращается в неверные крошки.
* Минус: один orphan делает 422 и для `/categories`, и для `/categories/tree`
  (осознанно: частично неверное дерево хуже явной ошибки).
* Минус: на каждом запросе читается весь список категорий; для больших
  деревьев понадобится кэш с инвалидацией по версии дерева в B2B.
