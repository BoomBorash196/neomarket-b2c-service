# ADR-008: идентификация пользователя в избранном (IDOR-защита)

## Контекст

US-CART-01: избранное покупателя с CRUD и обогащением из B2B. Нужно решить,
откуда брать `user_id` в endpoint'ах. Варианты из задания: из query-параметра,
из JWT claims, из заголовка `X-User-Id`.

## Рассмотренные варианты

| Вариант | Защита от IDOR | Сложность реализации |
| --- | --- | --- |
| **`user_id` из query-параметра** | Нет: любой клиент может подставить чужой id и прочитать/изменить чужое избранное | Минимальная |
| **`user_id` из JWT claims** (парсинг токена в B2C) | Высокая | Средняя/высокая: нужна валидация подписи, ротация ключей, обработка истечения |
| **`X-User-Id` (заголовок от доверенного шлюза)** | Высокая при условии, что шлюз ставит заголовок из проверенного JWT и клиент не может его подделать | Низкая: B2C просто читает заголовок и возвращает 401, если он пуст |

## Решение

Выбран **`X-User-Id`**: `user_id` берётся только из заголовка, query-параметры
и тело запроса игнорируются (IDOR-защита). Шлюз аутентификации проверяет JWT
и прокидывает `user_id` в заголовок, поэтому B2C не разбирает токен сам —
это снижает сложность и поверхность атаки, сохраняя защиту. Отсутствие
заголовка → `401 MISSING_AUTH`.

## Последствия

* Плюс: простая и тестируемая логика, IDOR закрыт на уровне контракта.
* Плюс: B2C не зависит от JWT-ключей и их ротации.
* Минус: безопасность опирается на корректную конфигурацию шлюза (заголовок
  должен удаляться/перезаписываться на границе, а не доверяться клиенту).
* Минус: при прямом обращении к сервису в обход шлюза заголовок можно подделать
  — в проде B2C доступен только через шлюз.
